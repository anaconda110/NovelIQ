# 从 0.2.1 升级到 0.3.0

入口：`scripts/migrations/migrate_0_2_1_to_0_3_0.py`。脚本默认只读预检，只有显式指定 `--apply --expect-database` 才执行数据库升级。

本入口按本次明确允许的旧数据转换例外实现，不修改仓库默认的“数据处理只允许重建”约束，不在正式读写链增加旧格式兼容。

## 数据范围

脚本以 0.2.1 发布标签中的实际 ORM 为源结构，以当前 0.3.0 ORM 为目标结构；两者均为 30 张业务表。配套 JSON 保存源表字段、类型、可空性、主键与外键目标，以及目标结构和约束摘要。项目版本仍只读取 `pyproject.toml`，不增加运行、模块或结果版本。

执行时先将全部源表整体移动到归档 schema，保留原表 OID、记录、索引、序列和外键；再在原业务 schema 建立新表并转换。默认归档名为 `<业务schema>_pre_0_3_0`，长名称取业务 schema 前 50 个字符后加后缀，也可通过 `--archive-schema` 指定。已经存在的归档不会被覆盖。

| 源数据 | 处理方式 |
| --- | --- |
| 小说、运行、章节、段落 | 转换身份并保存 UUIDv7 映射，原文、目录身份、章节编号和顺序原样保留；原运行状态保留，taskid 单独生成 |
| 成功标注工作与章级产物 | 核验实际 work、invocation、章节和角色后转换；`solo → annotation`、`structure → entity`、`event → event`、`evidence → metric` |
| 章级指标、段落情绪 | 转入具名指标和评估条目；缺失指标保持空值，不补写中性值 |
| 段落统计、主题权重、向量、LOWESS 结果 | 转入相应具名列与封闭特征种类，保留原数值和真实时间 |
| LTP 词元、依存弧、语义依存弧、NER 与短语命中 | 转入区间和弧表，核对词元原文；词元索引转为 0 起，ROOT 转为空端点，原弧顺序保留 |
| 图实体与关系 | 转换实体身份；关系只有在历史观察能证明唯一类型时转换，不选择或拆分历史关系类型 |
| 对话 | 只有真实创建工作、章节坐标和原文均可核验，且没有指向未转换旧事件时转换 |
| 模型与工具审计 | 保留用量、费用、计时和通信文档；无法可靠归属真实 Agent 的调用保留为独立调用，不伪造作者 |
| 旧事件、事件边、案例、图谱操作与状态 | 完整留档，缺少的新正文、案例类型、承诺人、操作顺序等不补造 |
| 旧诊断产物 | 完整留档；0.2.1 的正式保存入口没有记录生产 invocation，不能根据相近时间推断作者 |
| 旧 SSE 消息 | 完整留档，不使用旧身份载荷重放消息或伪造新幂等键 |

源表均完整留档。“转换”不表示原记录会被移除；无法转换的项目在 `archived_items` 中报告，并按原运行列出 `requires_reanalysis`。原文或来源矛盾、业务键冲突及约束失败会阻断升级并回滚，不自动清洗或修补。

这是数据库迁移入口。原始文件路径按登记值保留，脚本不改名、复制或转换外部模型文件。报告的 `external_artifacts.items` 列出原产物位置与运行身份；LDA/W2V 完成标志保留旧构建事实，不代表新身份对应的模型文件路径已经可读。需要复用外部模型时，仍须单独核对文件位置、配置和实际加载结果。

## 使用

从 0.3.0 发布代码运行。数据库连接使用 `.env` 中现有的平铺配置：`DATABASE_URL/USERNAME/PASSWORD` 或 `TEST_DATABASE_URL/USERNAME/PASSWORD`；schema 默认读取对应的 `DATABASE_SCHEMA` 或 `TEST_DATABASE_SCHEMA`，未配置时使用 `public`。

先在隔离的 0.2.1 备份恢复库预检：

```powershell
uv run python -m scripts.migrations.migrate_0_2_1_to_0_3_0 --database-env TEST_DATABASE --schema <业务schema> --report <新报告文件.json>
```

核对 `source_row_counts`、`converted_rows`、`archived_items`、`requires_reanalysis` 和 `external_artifacts`。`ready: true` 表示只读预检通过；数据库约束仍会在实际执行事务中验证，不表示全部旧结果可在新合同下直接复用。

执行前保留完整数据库备份和 0.2.1 发布代码，停止业务写入，并确认没有 `pending/running/cancelling` 任务或 `running` 模型调用。隔离演练和实际执行都要求明确匹配数据库名：

```powershell
uv run python -m scripts.migrations.migrate_0_2_1_to_0_3_0 --database-env TEST_DATABASE --schema <业务schema> --apply --expect-database <测试数据库名> --report <新执行报告.json>
```

实际发布时，将连接选择改为 `--database-env DATABASE`，同时明确填写实际 schema 和数据库名。脚本不会自动切换服务或重新运行分析。

## 执行保护与核对

- 预检事务只读，schema 不存在时拒绝，不回退到 `public`
- 源外键按 PostgreSQL 实际 OID 所指向的 schema 和表核对，缺失或跨历史 schema 引用会拒绝
- 执行使用事务级迁移互斥锁和源表停写锁，获得锁后重新检查源结构；等锁限时 5 秒，单条 SQL 限时 60 秒
- 新表、归档、数据转换、ID 映射、报告与最终约束校验在同一事务中完成，任何失败整体回滚
- 归档前后核对原表 OID 和全部源表行数；外部归档表引用原表的外键随原 OID 保留
- 新业务 schema 只有当前 30 张业务表；身份映射和执行报告写入归档的 `migration_ids`、`migration_report`
- 已是完整目标结构时返回 `already_migrated: true, applied: false`，不重复写入
- `--report` 不覆盖已有文件；退出码 `2` 表示阻断或执行失败。退出码 `3` 表示数据库已经提交，但本地报告写入失败，数据库内的执行报告仍保留

数据库升级不等同于分析结果重建验收；需要重新生成的结果仍通过正式流程从原始输入生成。归档 schema 也不能代替完整数据库备份。
